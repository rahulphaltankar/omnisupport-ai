# Field-level leakage register

Prediction moment **T0 = ticket creation, before human triage**. Generated by `scripts/01_data_audit.py` from `src/omnisupport/data/leakage.py` and enforced in code by `assert_raw_columns_allowed` / `assert_features_valid`.

| Field | Role | Available at T0 | Rationale |
|---|---|---|---|
| `ticket_id` | excluded_identifier | yes | Row identifier; carries no behavioural signal and would let a model memorise rows. |
| `customer_id` | excluded_identifier | yes | Used only as a CV/split grouping key to stop the same customer straddling folds. |
| `order_id` | excluded_identifier | yes | Identifier; sequential with ticket order so it can proxy time/ordering. |
| `image_id` | excluded_identifier | yes | Only 480 rows link to an image; used by the vision task, not by tabular models. |
| `timestamp` | feature_ok | yes | Ticket creation time: used for calendar features and for the temporal train/val/test split. |
| `support_channel` | feature_ok | yes | Known at creation. |
| `customer_region` | feature_ok | yes | Customer profile attribute; 'Unknown' retained as a category. |
| `customer_tenure_months` | feature_ok | yes | Account age at creation. |
| `product_category` | feature_ok | yes | Attribute of the order the ticket refers to. |
| `order_value` | feature_ok | yes | Order value in GBP known from the order system. |
| `delivery_delay_days` | feature_ok | yes | Delay observed by the carrier/order system when the ticket is opened (assumption A3). |
| `previous_ticket_count` | feature_ok | yes | Count of PRIOR tickets by definition, so excludes the current one. |
| `issue_title` | feature_ok | yes | Customer-entered title (30 distinct strings); written before triage. |
| `issue_description` | feature_ok | yes | Customer-entered message. |
| `attachment_available` | feature_ok | yes | Attachment uploaded by the customer at creation (assumption A4). |
| `issue_category` | excluded_assigned_at_triage | no | Operational label assigned by support staff after reading the ticket. Excluded from T0 tabular models (the text itself is the legitimate input); it is the target of the NLP classifier. |
| `priority` | excluded_assigned_at_triage | no | Assigned during triage and strongly outcome-linked; excluded to avoid circular prediction. |
| `customer_sentiment` | excluded_post_outcome | no | Documented as 'derived from post-contact review process'; escalation rate 43% vs 20% by sentiment. |
| `refund_requested` | excluded_ambiguous_timing | no | Timing of recording unclear and it is determined by issue type; excluded conservatively (no gain measured). |
| `refund_amount` | excluded_post_outcome | no | Known only after the case is handled. |
| `csat_score` | excluded_post_outcome | no | Collected after closure (knowledge_base/29_csat_followup.md); 56,852 missing. |
| `resolution_status_after_7d` | excluded_post_outcome | no | Status observed seven days later. |
| `final_agent_disposition` | excluded_post_outcome | no | 'specialist_escalation' is identical to escalated=1 (perfect leak). |
| `escalated` | target | no | Classification target: case routed to a specialist queue. |
| `resolution_time_hours` | target | no | Regression target: hours to operational resolution. |
| `customer_age_band` | evaluation_only_sensitive | yes | Age band: kept out of models (data minimisation / fairness); used only for subgroup evaluation. |
| `preferred_language` | evaluation_only_sensitive | yes | Language: kept out of models; used only for subgroup evaluation. |
| `accessibility_support_flag` | evaluation_only_sensitive | yes | Accessibility need: kept out of models; used for subgroup evaluation (ablation in ml_classification). |

## Empirical confirmation

`final_agent_disposition == 'specialist_escalation'` coincides exactly with `escalated == 1` (`artifacts/data_audit/escalated_vs_final_disposition.csv`). Single-field scores are in `artifacts/data_audit/single_field_leak_scan_escalated.csv`; the leakage-uplift experiment is in `artifacts/ml_classification/leakage_demonstration.csv`.
